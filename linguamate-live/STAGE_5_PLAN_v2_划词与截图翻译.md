## Context

LinguaMate 现有的主链路是「说」的一端：麦克风 → 腾讯 ASR → 净化 → 翻译（CN→EN）→ 460×260 悬浮窗。阶段 5 的 P1（5 段状态流 + spinner）和 P2（腾讯云 TTS 替换 speechSynthesis）已完成并验收。

缺的是「读」的一端：看到英文（论文、GitHub、邮件、聊天）时没有顺手的翻译入口。用户想在不切换窗口、不打断当前应用的前提下，选中即译、截图即译。

本计划新增两个输入模式，共用同一个浮动弹窗输出：

- **划词翻译**（v2 修订）：用户选中文字 → **连按两次 `Ctrl+C`** → 读取剪贴板文本 → EN→CN 翻译 → 在当前应用上方弹出小型悬浮译文
- **截图翻译**：全局热键 `Ctrl+Shift+S` → 全屏拖框截图 → 腾讯云 OCR → EN→CN 翻译 → 弹窗

### Windows 系统级的准确含义（避免实现范围误解）

本阶段目标是一个**在 Windows 桌面任意前台应用中都可按快捷键唤起**的工具，而不是只为 Chrome、Word 或 VS Code 做插件：

- 划词翻译**不使用全局热键**，也不监听键盘。它监听的是**按键的结果**：短时间内出现两次剪贴板变更。用户的每一次 `Ctrl+C` 都**照常生效、不被拦截、不被吞掉、不被改变**。
- 划词翻译的主通道是**剪贴板**——用户自己复制出来的内容。备用通道是 UI Automation 读系统选区（实测：记事本与 Edge 可用，Chrome 不可用）。
- **单次 `Ctrl+C` 必须完全无感**：不弹窗、不发请求、不记录内容。这是本功能的硬性验收项，不是体验优化。
- 读取不了时不猜、不自动截图，只显示「此内容无法读取，可使用截图翻译」。
- `Ctrl+Shift+S` 是 Windows 全局热键；注册成功后，无论当前前台是什么应用，用户都能触发截图翻译。
- 截图翻译是系统级兜底：任何用户能正常框选并被系统截取的可见内容，都应能走 OCR 与翻译；受 DRM/硬件保护导致的黑屏是已知例外。
- Notepad、Chrome、Edge、Word、VS Code 只是步骤 0 的**代表性兼容性样本**，不是功能支持范围的白名单，也不是产品入口的限制。

两者都遵守产品现有的核心原则：**永远给用户一个可以否决的面板，绝不修改用户的文档或输入。** 这是本产品与「无感注入」类翻译工具的差异点，不因为加了新功能而放弃。

**工作量**：11–16 天（预研门槛 + 7 个实施步骤）。v2 修订后，工作量主要变化在步骤 0（新增双复制机制预研）与步骤 3（新增剪贴板主通道）；截图翻译部分不受影响。每步完成后停下汇报，等用户检验再继续。

### 隐私与数据边界（新增，必须实现）

- 选区文本和截图仅在用户**明确触发后**发送给配置的云端翻译/OCR 服务；不默认保存历史、不写业务日志。
- 第一次使用“划词/截图翻译”前显示一次简短说明：内容将发送至已配置的云服务；用户确认后才请求。后续可在设置中重新查看。
- 临时 PowerShell 输出文件和截图 Buffer 使用唯一临时路径；无论成功、超时、取消还是程序退出，都在 `finally` / 退出钩子中清理。不得把截图落到项目目录。

#### 剪贴板专项（v2 新增，逐条可验收）

- **单次 `Ctrl+C` 完全无感**：不弹窗、不发请求、不记录内容、不产生任何副作用。实现上必须用「连续两次变更」判定，不得用「检测到一次变更」判定。
- 剪贴板内容**只在双复制动作被确认之后读取一次**，只在内存中短暂存在，用完即弃。
- 触发时读到的内容必须来自**本次第二次变更之后的一次全新读取**，绝不复用上一次的内容。若第二次变更后拿到的是空内容或非纯文本（复制了图片、剪贴板被清空等），一律**不得**翻译，并引导使用截图翻译。
- 「陈旧」的定义是**事件层面**的：只发生了一次复制、或两次复制间隔过远，都不触发。**不是**靠比较两次文本是否相同来判定——实测对同一选区连按两次 `Ctrl+C`，两次文本本来就完全相同。
- **零写入**：整个流程不调用任何写剪贴板 API。验收时必须核对用户剪贴板在触发前后完全一致。
- 任何情况下**不得**把选区文本或剪贴板内容写入日志、诊断文件、崩溃报告或历史记录。诊断脚本的输出文件只能包含长度、来源应用、是否成功等元数据。

## 关键技术决策一：划词主通道 = 双 Ctrl+C + 剪贴板

**目标动作**：用户选中文字 → 连按两次 `Ctrl+C` → 读剪贴板 → 悬浮译文。

**核心约束**：不得拦截 `Ctrl+C`。因此**不监听按键**，而是监听按键的**结果**——剪贴板变更。用户在短时间内产生**两次**剪贴板变更，即视为显式双复制触发。

**本方案成立取决于一个尚未验证的前提**（新步骤 0 的第一要务）：

> 用户已选中文字时，**第二次** `Ctrl+C` 是否会让 Windows 剪贴板序号 `GetClipboardSequenceNumber()` 继续递增？
> 若应用对「内容与剪贴板相同」的复制做了去重、不再写入剪贴板，则第二次不产生变更，双复制手势根本检测不到，必须改换触发方式。

**在新步骤 0 证明该前提之前，不得编写任何产品代码。**

### 桥接方案对比（上限两种，禁止引入大型库 / 键盘 Hook 库 / 原生依赖）

| | **方案 A：剪贴板序号监听** | **方案 B：剪贴板内容变更监听** |
|---|---|---|
| 机制 | PowerShell 子进程循环调用 Win32 `GetClipboardSequenceNumber()`，**只上报序号，不读内容** | Electron 主进程轮询内置 `clipboard.readText()`，在内存中与上一份比对 |
| 新增 npm 依赖 | 无 | 无 |
| 额外机制 | 需 `Add-Type` + P/Invoke 声明（`kernel32`，PowerShell 随 Windows 自带） | 纯 Electron 内置模块 |
| 打包影响 | 零新增文件；脚本运行时写临时目录，`build.files` 不变 | 零，纯主进程代码 |
| 隐私强度 | **强**：平时只知道「变了」，完全不知道内容 | 弱：持续把用户剪贴板文本读进内存（虽不落盘、不发送） |
| 心跳开销 | 50–80ms 一次，只取回一个整数 | 50–80ms 一次，每次跨进程读文本 |
| 主要风险 | 第二次复制被应用去重 → 序号不递增 → 触发不到 | 同上；另有跨进程读文本抖动/超时风险 |

**倾向方案 A**：隐私边界最干净，符合本产品「不记录用户内容」的核心原则，且同样零 npm 依赖。
两者的前提风险**完全相同**，所以必须先用新步骤 0 判定前提是否成立，再二选一；不得跳过前提直接选型。

## 关键技术决策二：备用通道的选区读取不用 FFI

> 本节描述的 UIAutomation 实现**降级为备用通道**，仅在主通道拿不到新纯文本时尝试。
> 它的价值依然明确：Edge 默认可读（42 个可读节点）、Notepad 可读，因此是主通道失效时的有效补充。

**原设想**：`ffi-napi` 调 `uiautomationcore.dll` 的 COM 接口。

**改为**：PowerShell 子进程 + Windows 自带的 `UIAutomationClient` / `UIAutomationTypes` .NET 程序集。

理由：

1. **打包安全**——这是 Electron + electron-builder 应用，原生模块需要 `electron-rebuild` 且 ABI 极易在 `npm run dist` 阶段炸掉。零新依赖则 dev 和打包后行为完全一致。
2. **零安装成本**——`UIAutomationClient` 随 Windows 自带，用户不需要装任何东西。
3. **编码可控**——本项目在 P2.1 调试时已验证「写 UTF-8 临时文件 + `fs.readFileSync` 读回」能绕开 PowerShell stdout 的中文乱码。沿用同一手法。
4. **代价可接受**——每次约 300ms 进程启动，对「按热键 → 弹窗」这个交互无感知。

覆盖范围（以步骤 0 实测为准，不写"预期"）：

| 应用 | 默认设置下 UIA 实测结果 |
|---|---|
| 记事本 Notepad | ✅ 可读，44 字符逐字一致，~120ms |
| Microsoft Edge | ✅ 可读，490 节点 / 2 Document / 51 Text / 42 个可读选区节点 |
| Google Chrome | ❌ 不可读，4 节点空壳，停在 `Chrome Legacy Window`；轮询、事件订阅、`--force-renderer-accessibility` 三种方式均失败 |
| VS Code | 本机未在标准路径找到，未测（**不得计入通过数**） |
| Word | 已安装，未测 |

未覆盖的 Chromium 应用、以及自绘 renderer、游戏 UI、DRM 保护内容：UIA 返回空 → 走主通道（剪贴板）→ 仍失败则提示使用截图翻译。**截图翻译永不自动触发。**

3. **普通单次 `Ctrl+C` 必须完全无感**：不弹窗、不发请求、不记录内容、无任何副作用。
4. 在 Notepad、Chrome、Edge、WPS Office（用户机器上 `.docx` 的实际默认打开程序，**经用户确认代表 Word 一类办公软件**）中验证是否拿到正确文字。VS Code 与 Microsoft Word 本轮**未测**（Word 已确认安装于 `C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE`，但用户未实际启动它；VS Code 本轮未纳入）。
5. **无选区、复制图片、密码框、复制失败**时：不得发送旧剪贴板内容，不得误触发翻译。
6. 全程不得把选区或剪贴板内容写入日志、诊断文件或历史记录。
7. 现有 UIA 探针只用于量化备用通道覆盖率，**不作为主路线是否继续的依据**。

**通过标准（预研范围）**

- Chrome、Edge、Notepad 三个应用均能稳定完成「选中 → `Ctrl+C` `Ctrl+C` → 拿到**与选区逐字一致**的新文本」；
- 单次 `Ctrl+C` 零干扰（有对照证据：单次复制不触发任何输出）；
- 「第二次复制没有产生新纯文本」时被正确识别为**不触发**，而非回退去翻译旧内容；
- 读取耗时在可接受范围（建议 ≤500ms，从第二次复制到拿到文本）；
- 探针输出文件在成功与失败后均已清理。

#### 步骤 0 实测结果（2026-09-28 完成，结论：有条件通过）

探针：`.tmp-uia-probe/dclip.ps1`。只调用 `GetClipboardSequenceNumber()`（只回答剪贴板**是否**变了，从不回答**里面是什么**），并在检测到变更后调一次 `Get-Clipboard` 仅用于测量**长度**与 **SHA-256 前 16 位指纹**。**文本本身从未落盘、从未打印、从未发送。**

| 应用 | 复制次数 | 序号变化 | 指纹 | 双复制可检测 | 备注 |
|---|---|---|---|---|---|
| Notepad（两轮独立复测） | 3 + 3 | 2952→2960/2968/2976；3038→3046→3054 | 双复制两次**完全相同** | ✅ 间隔 3832 / 2515 ms | 两轮结果一致，可重复 |
| Chrome | 3 + 1 干扰 | 2987→2994/3001/3008 | 双复制两次完全相同 | ✅ 间隔 2547 ms | 另有一条 `len=0` 空剪贴板事件（见下） |
| Microsoft Edge | 3 | 3161→3170/3179/3188 | 双复制两次完全相同 | ✅ 间隔 1380 ms | `-PollMs 10`，三次全部 `app=msedge` |
| WPS Office | 4 | 3079→3104→3129→3154 | ⑥⑦ 完全相同 | ✅ 间隔 2240 ms | ⑤⑥ 间隔 22189 ms，**不应触发** |

**三条由实测推翻/修正的原设计：**

1. ✅ **主假设成立**：四个应用（含 Notepad 两次复测）对**同一选区**连按两次 `Ctrl+C`，`GetClipboardSequenceNumber()` **都会继续递增**，指纹一致。**双 `Ctrl+C` 不需要键盘钩子即可检测。**
2. ⚠️ **一次 `Ctrl+C` 使序号跳 7–8 次**（Windows 依次写入 CF_TEXT / CF_UNICODETEXT / HTML 等多种格式，每种各加一次）。因此**绝不可按序号变化次数判定**，只能按时间去抖。但把轮询压到 10ms 后实测「一次复制 = 一个事件」，说明去抖窗口开小即可。
3. ⚠️ **原「第二次文本与第一次相同 ⇒ 判为陈旧」的规则是错的**，会直接杀死主用例（用户对同一选区双复制本来就是主用例）。已改为**按事件次数**判定，详见步骤 3。

#### 步骤 0 补充验证：「与选区逐字一致」已关闭

前一轮探针只记录**长度 + 指纹**，因为写文本是被禁止的。它能证明「两次复制读到同一段文本」，但证明不了「这段文本和选区逐字相同」。为补上这一条，新增探针 `.tmp-uia-probe/vmatch.ps1`：

> **两个字符串只在内存里比较。** 两者都不写入结果文件、不打印、不发送。输出 JSON 里**只有** verdict、两个长度、进程名、节点数、耗时——**刻意不含指纹**，避免有人用已知明文反查。

| 模式 | 应用 | verdict | 剪贴板长度 | 对照侧长度 | 结论 |
|---|---|---|---|---|---|
| Uia（读活动窗口选区与剪贴板比对） | Notepad | **match** | 49 | 49 | ✅ 逐字一致，仅走 6 个节点 |
| Expect（预期串传入后内存比对） | Chrome | **match** | 44 | 44 | ✅ 逐字一致 |

Chrome 的 44 字符与早期 UIA 探针**独立读到的 44 字符**交叉吻合，两条互不依赖的证据指向同一段文本。

> 注：`copiesSeen: 1` 是设计使然——本探针在第一次复制后即比对退出，它的职责是「逐字一致」；「双复制可检测」由 `dclip.ps1` 单独验证，两者互不替代。
> 注：Expect 模式下的预期串会留在用户 shell 历史里，因此只能用一次性测试句，**不得用真实内容**。

**仍无实测数据的三项（设计上有防线，须在步骤 3 补验）：**

- **无选区按 `Ctrl+C`**：Windows 约定无选区时不改写剪贴板 ⇒ 序号不变 ⇒ 无事件 ⇒ 天然不触发。**步骤 3 已实测通过**（见下方「步骤 3 实测结果」）。
- **复制图片 / 复制失败**：序号会变，但读到的是非纯文本。**已实测到一次 `len=0 hash=E3B0C44298FC1C14`（空串的 SHA-256）**——证明「读到空内容」是真实会发生的场景，**读后必须判空并放弃，不得回退去翻译旧内容**。图片复制的具体形态已在步骤 3 实测。
- **密码框**：浏览器本身即阻止密码进剪贴板；**步骤 3 已实测通过**。

**触发窗口取值 —— 用户已于 2026-09-28 决定：去抖 250–300ms + 触发窗口 1000ms。** 预研阶段实测到的同选区双复制间隔为 1380 / 2240 / 2515 / 3832 / 4288 ms，**全部超过原计划写的「≤600ms」窗口，该数值已作废**。1000ms 按真人双击节奏（通常 100–500ms）留约两倍余量。**该取值已于步骤 3 用真实手势复验：用户实际双击间隔 600ms 与 500ms，两次都落在窗口内成功触发，1000ms 无需调整。**（预研那批 1380–4288ms 是测试脚本自己的按键节奏，不是人手节奏，不应据此上调。）注意：「复制两次」与「双击复制」在系统层面是同一个动作、无法区分，这是该交互的固有代价，只能靠窗口大小取舍。

**本步骤不能证明的事（须在汇报中写明，避免验收期误解）**

预研只验证**机制**，无法验证「正确的悬浮译文」与「不干扰 `Ctrl+Shift+L` 录音」——这两项需要产品代码，必须留到步骤 3 / 步骤 6 才能验收。本步骤通过 ≠ 功能可用。

**不通过分支**
- 若第二次 `Ctrl+C` 不产生剪贴板变更：**停止**，不进入步骤 1。向用户汇报实测数据，并由用户决定改换触发方式（例如改用「复制后按一个独立热键」「拖选即译」等），**不得擅自更换交互**。

**汇报**：一张「应用 / 是否安装 / 原文 / 实际读到 / 是否逐字一致 / 耗时 / 结论」表格，附单次复制零干扰与旧剪贴板保护的证据截图，并明确写 Go 或 No-Go、或「需要用户决定」。

#### 步骤 2 结果（2026-09-29）：✅ 打通。根因是我们自己的一个参数

`/v1/ocr` 真实调用**已成功**。此前长时间卡在 `FailedOperation.OcrFailed`，第一轮排查把它归给了「腾讯侧」——**那个结论是错的**，而且是本项目自己写错的一个参数造成的。

##### 根因：`PdfPageNumber: 0`

该参数是**从 1 开始**的页码。传 `0` 越界后，腾讯不回参数错误，而是笼统地回 `FailedOperation.OcrFailed`，与「图片有问题」完全无法区分。

逐参数拆解（每组跑 2 次，全部确定性复现，无偶发）：

| 载荷 | 结果 |
|---|---|
| 裸 `ImageBase64` | OK · OK |
| `+ LanguageType: 'auto'` | OK · OK |
| `+ IsPdf: false` | OK · OK |
| `+ PdfPageNumber: 0` | **OcrFailed · OcrFailed** |
| 后端当时的完整载荷 | **OcrFailed · OcrFailed** |

原样跑 10 次：**10/10 全失败**。所以既不是图片、也不是留白、也不是区域、更不是签名——是载荷里那个 `0`。

##### 关键的方法教训

前一轮我调的是**参数**（图片尺寸、空白比例、`LanguageType` 取值、区域），从来没换过**接口**。直到临时打一次 `GeneralHandwritingOCR`，同一张图 conf=99 成功，才意识到该怀疑「这个 action 是不是整体有问题」——而实际是这个 action 收到了非法参数。

**遇到笼统的业务错误，除了调参数，还要换一个接口打一次做对照。** 一个接口失败、同一服务的另一个接口成功，指向的是调用方而非服务方。

##### 第二个 bug：段落号读的是臆想的形状

打通后发现三行正文被并成一段。`readOcrParagNo` 按数组取 `Parag[0].ParagNo`，但腾讯真实返回的是**对象**：

```
{"Parag":{"ParagNo":1}}      ← 真实
{"Parag":[{"ParagNo":1}]}    ← 代码和测试假设的
```

`Array.isArray` 恒为 false → 段号永远读不出来 → 每张图都退化成单段 → 计划里「按段落逐段翻译」**从未真正生效过**。

而 `ocr.test.js` 里 5 处用例都用数组形状——**测试是照着一个不存在的 API 写的**，所以抓不到。已全部改成真实形状，并新增「两种形状都能解析」与「载荷不含 `PdfPageNumber`」两条回归。

回归保护做过变异验证：把 `readOcrParagNo` 改回数组版 → 3 条用例变红；还原 → **38/38 全绿**。

##### 真实调用结果

```
分块图 1200×700（标题/正文/标题/正文）
  → 200，4 段
  [0] conf=99  "Deployment Guide"
  [1] conf=99  "This document explains how to deploy the\nservice on a production cluster."
  [2] conf=99  "Database Setup"
  [3] conf=99  "Run the migration script before the first\ndeployment to create the required tables."

单段图 1100×284（三行连续正文）
  → 200，2 段
```

段落切分与视觉分块一致，标题与正文不再揉成一坨。

##### 顺带确认的正向事实

- TC3 签名有效（腾讯返业务错误而非 `AuthFailure`，且打同一密钥的 TTS 200）
- `GeneralHandwritingOCR` / `GeneralAccurateOCR` / `EnglishOCR` 均可用，错误码透传机制有效
- `GeneralBasicOCR` **是认 `LanguageType` 的**——上一轮「LanguageType 取值」那一整行排查结论作废
- `GeneralDocumentOCR` 在 2018-11-19 版本下不存在（`InvalidAction`）

此前因「服务未开通」而修的 `UnOpenError` 不可重试判定**仍然正确**，保留。

##### 腾讯云在线调试器（备用路径）

控制台产品下拉要选**文字识别（OCR）2018-11-19**，不是云服务器。参数是 `ImageBase64` / `ImageUrl` 二选一，都填时 `ImageUrl` 优先；`ImageBase64` 粘**纯 base64，不带 `data:image/png;base64,` 前缀**。不过既然本地直连已通，控制台只作为出问题时找腾讯的旁证。

#### ❌ 已作废：曾由步骤 2 派生的「裁掉纯色边缘」结论

曾写过「腾讯对文字只占画面一小块的图更容易 `OcrFailed`，所以步骤 5 必须 trim blank borders」。**该因果关系不成立**，已证伪：裁到文字铺满画面的 1100×284 图，在根因未修时照样 `OcrFailed`；而根因是载荷里一个字符，与留白毫无关系。

步骤 5 的 trim **仍然要做，但理由只剩省配额与更快**，不再声称它能提高成功率。

  - **判定依据是「事件次数」，不是「文本是否变化」**。⚠️ 实测证据：用户在记事本和 Chrome 中对**同一选区**连按两次 `Ctrl+C`，两次读到的文本**完全相同**（指纹一致）。因此**绝不能**把「两次文本相同」当作陈旧判据——那会直接杀死主用例
  - **陈旧判定（经实测修正）**：
    1. 必须观察到**两次独立的剪贴板变更事件**且间隔在触发窗口内；只发生一次 → **不触发**，不读剪贴板、不发请求、不记内容
    2. 第二次事件发生后**当场重新读取**剪贴板，**绝不复用**上一次触发时读到的内容
    3. 读到的纯文本为空、或非纯文本（复制了图片、剪贴板被清空等）→ 判失败，**不翻译**
    4. 两次事件间隔超过窗口 → 视为两次无关的普通复制，**不触发**
  - **时间去抖（禁止按次数判定）**：实测一次 `Ctrl+C` 会让剪贴板序号**跳 7–8 次**（Windows 写入多种剪贴板格式，每种各加一次）。因此判定**必须**按时间去抖：观察到变更后静默 250–300ms，把该窗口内的连续递增**合并为一次复制事件**。即便把轮询间隔压到 10ms，Notepad 与 Chrome 实测仍是「一次复制 = 一个事件」，说明去抖窗口开小即可，但去抖逻辑仍必须存在（不能依赖轮询恰好只抓到一次）
  - 主通道失败 → 调用备用通道 `readActiveSelection()`（UIA）
  - 备用通道也失败 → 返回 `{ status: 'unreadable' }`，由 UI 显示「此内容无法读取，可使用截图翻译」。**绝不触发截图。**
  - **零剪贴板写入**：本模块不得调用任何写剪贴板 API
  - **单次变更必须静默**：只有「两次」才触发；「一次」直接丢弃，不产生任何 UI / 网络 / 日志副作用
- `linguamate-desktop/src/selection-reader.js`（新文件，**降级为备用通道**）
  - 用 `child_process.execFile('powershell.exe', ['-NoProfile', '-NonInteractive', '-ExecutionPolicy', 'Bypass', '-File', scriptPath])` 调一个**落盘的 .ps1 脚本**（不是 `-Command` 内联——内联是本项目踩过中文乱码的坑）
  - 脚本内容：`Add-Type -AssemblyName UIAutomationClient, UIAutomationTypes` → 定位**当前有键盘焦点的控件** → BFS 找支持 `TextPattern` 的节点 → `GetSelection()` → `GetText(-1)` → **以 base64 走 stdout 返回**
  - ⚠️ **扫描根用 `FocusedElement`，与本节原文相反。** 原文要求扫窗口根，理由是「取焦点元素会只扫到 3 个工具栏节点」——那是因为当时运行脚本的 PowerShell 窗口自己占了焦点。实测发现扫窗口根会引入更严重的问题：**静态文本控件（状态栏、缩放比例）会向 UIA 报告一个看起来合法的选区**。实测在画图里全选图片后，状态栏的 `100%` 被当成用户选区抓回来当翻译输入——触发逻辑完全正确，读到的内容完全错误。用户真在选文字时那段文字必然在焦点控件里，状态栏不在焦点上。焦点控件不属于前台进程时**直接判失败（`focus-elsewhere`），绝不退回全窗口扫描**
  - **文本以 base64 走 stdout，不落盘**（与本节原文的「写入 UTF-8 临时文件」相反）。原文自相矛盾：一边要求临时文件只写元数据不写文本，一边又要求调用方拿到文本。base64 是纯 ASCII，绕开了当初选择临时文件的原因（PowerShell stdout 中文乱码），而用户选中的内容自始至终没有落过盘
  - **脚本必须纯 ASCII**：PowerShell 5.1 读无 BOM 的 `.ps1` 会按 ANSI/GBK 解释，**乱码字节会吞掉行尾换行**，把下一行并进注释——表现是某段代码「莫名其妙没执行」，且**退出码 0、stderr 全空**。这是排查过程中真实踩到的
  - Node 侧解析 stdout；每次用 `fs.mkdtemp` 创建独立目录。⚠️ **清理必须挂在 Promise 回调上，不能用 `finally`**：`return new Promise(...)` 写在 `try` 里时 `finally` 会在返回那一刻立刻执行，目录会在 PowerShell 读到脚本之前被删掉，子进程报「-File 的参数不是实际文件路径」，整条备用通道 100% 静默失效
  - 导出 `readActiveSelection()` → `{ text } | null`；非 Windows 直接返回 null；异常一律吞掉返回 null（不 crash）
  - 加 3s 超时（`execFile` 的 `timeout` 选项）
- 脚本落盘位置：临时目录运行时生成（`os.tmpdir()`），**不打进安装包**——内容是固定字符串，不需要单独文件

#### 修掉的 3 个真实缺陷

**① `popup:copy` / `popup:close` 挂在 `win.webContents.on` 上——两个按钮都是死的**

渲染层 `ipcRenderer.send()` 的消息只到 **`ipcMain`**；`webContents.on` 收的是「主进程发给渲染层」的消息。表现是 `[复制]` 点了没反应、`[×]` 关不掉，**且没有任何报错**。与步骤 4 早先修的 `ipcMain.handle` / `ipcRenderer.send` 是同一类配对错误，但那次我只把 `popup:resized` 改对了，漏了这两个。

**这个 bug 单测查不出来，而且是被自己的测试结构掩盖的**：当时的假 Electron 把 `handle` 和 `on` 塞进同一个 Map，测试又直接在 `win.webContents` 上 emit 来模拟「渲染层发消息」——**测试的模拟方式与错误实现是镜像的**，结构上就不可能发现。改法：假件拆成 `invokeFromRenderer` / `sendFromRenderer` 两条独立通道，后者只投递到 `ipcMain.on` 注册过的 handler。改完之后把生产代码退回原写法，**14 个测试同时变红**。

**② 长译文时原文区溢出，压在译文上（截图才发现）**

`.source` 写成 `flex: 0 1 auto` + `min-height: 0`，内容一多 flex 真的把它压矮；而 `.source-text` 仍按自然高度绘制、`.source` 又没有 `overflow: hidden`，于是原文第三行**画到了盒子外面**，正好盖住译文第一行。单测看不见 CSS 布局，只有截图能看见。改成 `flex: 0 0 auto` + `overflow: hidden`，压缩全部交给有 `min-height:0 + overflow-y:auto` 的译文区。

**③ 新写的回归测试被自己的注释骗过去了**

给 ② 加测试时，断言的正则 `/flex:\s*0\s+0\s+auto/` **匹配到了 CSS 注释里那句解释 bug 的 `flex:0 0 auto`**，而不是真正的声明。把 `.source` 改回可压缩，测试照样全绿。修法：断言前先 `replace(/\/\*[\s\S]*?\*\//g, '')` 剥掉注释。这正是「只在正确代码上通过的测试什么都证明不了」的又一次实例——必须回退修复确认它变红。四条断言逐条变异，全部变红。

**④ 顺带补上的安全缺口**：`popup:copy` / `popup:close` 原本没有 sender 校验，任何能发 IPC 的窗口（比如悬浮窗）都能伪造 `popup:copy` 让本应用写剪贴板，直接违反「剪贴板只在用户显式点 [复制] 时写」这条硬约束。已加校验 + 两条测试（外来 sender 拒绝、自己窗口仍可用）。去掉校验的变异确认会红。

**修掉的 2 个真实缺陷**

**① 一次划词建了两个弹窗窗口，用户看到的是「闪一下、跳一下」**

`onCaptureStart`（正在读取…）和 `translateSelection`（正在翻译…）各调一次 `showTranslationPopup`，而它每次都 `destroy()` 旧窗并重新读一次前台矩形（多起一个 PowerShell，约 300ms）。证据是每次捕获都有**两行** `[popup] foreground=`。改法：`onCaptureStart` 存下它返回的 Promise，`translateSelection` 优先 `await` 它再原地 `update()`，不另起窗口。改后每次捕获只有一行。

**② 前台窗口是自己时，弹窗会以自己的窗口为锚点**（步骤 4 遗留项，已处理）

`readForegroundRect()` 只取 `GetForegroundWindow()`。点过托盘之后前台就是 LinguaMate 自己的悬浮窗，「出现在当前应用上方」这个语义整个作废。改法：脚本多输出一个窗口所属 PID，`readForegroundRect` 发现它等于 `process.pid` 就返回 `null`，退到光标定位。**必须在读矩形的同一次调用里判定**——弹窗一旦出现前台就变了，事后另查来不及。已做变异验证：把判断去掉，该测试变红。

**发现的边界：间隔 < 280ms 的双 `Ctrl+C` 不会触发（未改动，需用户决定）**

真机量到：**一次复制在剪贴板序号上是「一次」原子变更**（OpenClipboard / EmptyClipboard / SetClipboardData 三个调用在 69ms 内走完，序号只跳 1 次）。计划里「一次 `Ctrl+C` 跳 7–8 次」是富文本来源复制才有的形态。

于是 `DEBOUNCE_MS = 280` 的实际后果是：两次复制间隔小于 280ms 时，第二次变更会把第一次的去抖计时器**重置**，两次被合并成**一个**落定事件 → 不触发。**可触发区间是 [280ms, 1000ms]。**

本机不受影响——用户 2026-09-28 用真实手势复验过，自己的双击间隔是 500ms 与 600ms，离下界很远。**但这是真实边界**，节奏极快的人会觉得划词「偶尔不灵」。缩短去抖能覆盖，代价是更依赖「一次复制 = 一个事件」这个前提。

**处理方式：没有擅自改。** 250–300ms 是用户 2026-09-28 明确拍板的值，且已用真实手势复验。已把该行为写成**刻画测试**（锁住 `[去抖, 触发窗口]` 这个区间，含 `<去抖` 与 `>窗口` 两侧的反例），要改请先与用户确认。

#### 弹窗改为抢焦点以支持 Esc（2026-09-30，用户实机验收后发现）

**现象**：步骤 6A 验收时用户报「测试通过，但**不能按 Esc 退出**」。

**根因是两条同时成立，缺一不可**：

1. `focusable: false` —— 窗口永远拿不到焦点，键盘事件进不来；
2. `popup.js` 里压根没有 `keydown` 监听（当时的测试还**断言**源码里不许出现 `keydown`/`Escape` 字样）。

这**不是步骤 6 接线弄坏的**，是步骤 4 就定下的设计，且计划第 531 行明文写了「不得通过把 `focusable` 改为 true 来保留 Esc，**除非用户明确接受打断当前工作**」。

**顺带查出第二件事**：弹窗**没有任何自动消失机制**——无 `blur`、无超时、点外部无效。唯一的关闭入口是要精确瞄准的 [×]。所以痛点其实有两个，Esc 只是其中一个。

**用户的决定**：抢焦点，Esc 立刻可用（明确接受打断当前工作，计划第 531 行的前置条件由此满足）。

**改动**

| 位置 | 改前 | 改后 |
|---|---|---|
| `popup-manager.js` | `focusable: false` | `focusable: true` |
| `popup-manager.js` | `win.showInactive()` | `win.show()` |
| `popup/popup.js` | 无 keydown 监听 | `keydown` 监听，`Escape` → `api.close()`（与 [×] 同一个 `popup:close` 通道） |
| 测试 | 断言 `focusable === false`、断言 popup.js **不得**出现 `keydown`/`Escape` | 断言 `focusable === true` 且显示时**真的拿到焦点**；把 keydown handler 抽出来**真跑一遍** |

**验证**：90/90 通过。三个变异各自打红正确的那条测试——把 `show()` 改回 `showInactive()` / 删掉整个 keydown 监听 / 把 `!==` 写成 `===`。确认断言不是摆设（教训：写「不许出现某字样」的测试很容易在行为完全相反时仍然变绿）。

**代价（用户已知并接受）**

- 弹窗一出现就抢焦点：原应用的选区、光标位置、输入法状态被打断。
- 弹窗是 `alwaysOnTop` 且盖在应用内容上，它持焦点期间**后续按键被弹窗吞掉**——输入是真的丢，不只是看不见。
- **边界**：Esc 只在弹窗持有焦点时有效。用户点回原应用继续干活后，Esc 就回到原应用去了，弹窗不会跟着关。

**仍然不做的两条路**

- ❌ 弹窗可见期间用 `globalShortcut` 全局注册 `Escape`：会在**全系统**吞掉 Esc（用户在别的应用里按 Esc 取消对话框会被吃掉）——与划词「不吞掉用户 Ctrl+C」是同一类违规。
- ❌ 低级键盘钩子（`WH_KEYBOARD_LL`）：要引原生模块，与本计划「零新依赖、零原生模块」的立身之本冲突，且打包 ABI 易炸。

**未机器验证**：真实按键本身（真实 `Esc` 键 → 弹窗关闭）由用户在实机确认。自动发送合成按键去驱动另一个进程的置顶窗口，既脆弱又会干扰用户桌面，不值得为这一行接线搭一套。

##### 点弹窗以外即关（同日追加，用户在拿到 Esc 之后接着提的）

**实现方式：`win.once('blur', () => destroy())`，挂在 `show()` 之后。**

**为什么不铺一个全屏透明窗口吃点击**——那是「点击外部」最直觉的写法，但它会连带把用户对**原应用**的点击一起吃掉。而弹窗没有自动消失（会一直挂着直到被关掉），于是原应用在弹窗存在期间**彻底点不动**。`blur` 是零成本的等价物：在 Windows 上点别处就是换焦点，顺带还覆盖 Alt+Tab 和任务栏点击，零新增窗口、零新增依赖、零输入拦截。

**为什么挂在 `show()` 之后而不是建窗时**：建窗到亮相之间窗口还没显示，那段时间的焦点事件不代表用户「看了弹窗又不要了」。

**测试**：两条 + 变异验证——删掉整个监听 → 第一条红；把监听挪回建窗处 → 第二条红。

**已知边界（照实说）**：`blur` 的语义是「失去焦点」，不完全等于「在任意位置点了鼠标」。极少数不参与激活的窗口（某些置顶工具窗、通知气泡）被点时可能不换焦点，那种情况下弹窗不会关。真要覆盖它就得回到全屏拦截层的方案，代价是原应用点不动——不划算。真实鼠标点击由用户在实机确认。

## 已解决的实施约束（Claude 不需要再次向用户提问）

### A. 步骤 6 坚持「只加不改」，但明确运行中重绑限制

`main.js:154` 现状：

```js
function registerShortcut(accelerator) {
  globalShortcut.unregisterAll();   // ← 第一行就清空所有全局热键
  ...
  globalShortcut.register(accelerator, ...)
}
```

本计划**不改**这个函数，改在旁边新增 `registerExtraShortcuts()`，内部只有 `globalShortcut.register()`。

- **理由**：改 `registerShortcut` 为「支持多热键」是更干净的做法，但它会重写录音热键的注册路径。一处写错，`Ctrl+Shift+L` 录音直接失效，且故障可能延迟暴露。
- **代价**：`registerShortcut` 与 `registerExtraShortcuts` 各管各的，两处都要处理冲突 / 失败提示，存在轻微重复。
- **落实方式**：Electron 的 `globalShortcut.register` 返回 `false` 时视为该快捷键未注册；必须分别处理并报告。注意：这不是“零风险”，因此步骤 6 必须执行录音回归和冲突测试。当前阶段不做运行中重绑；未来若做设置页，另开计划统一重构注册器。

### B. JEV 不作为工程门禁

原计划在步骤 1 之前跑一次 `typesafe-jev` 决策模型（评估方案风险等级 / 步骤顺序 / 兜底可接受度）。**实际调用返回 HTTP 400 未跑通**，因此**从未拿到任何 JEV 结论**，本计划的步骤顺序也**不是** JEV 推荐的结果。

- **落实方式**：可按用户要求保留 JEV 记录，但无论成功或失败均不阻塞步骤 0。密钥只在进程内 Authorization header 中使用，不进入命令行、磁盘或日志。

### C. 录音功能回归基线先固定

步骤 7 的回归要求「录音链路未受影响」，但**基线未固定**。建议在动工前先录一次现状（麦克风说两句 → 中文净化稿 + 英文翻译 + 复制 + 朗读），作为对照。

### D. 既有临时文件不自动删除

`backend/` 下现存 5 个调试残留（**不随本计划自动删除，等你确认**）：

| 文件 | 来源 |
| --- | --- |
| `.tmp-tts-test.js` | P2.1 调试 |
| `.tmp-tts-out.mp3` | P2.1 调试 |
| `.tmp-jev-state.json` / `.tmp-jev-questions.json` / `.tmp-jev-call.ps1` | 上一轮 JEV |
| `.tmp-jev-gate.ps1` / `.tmp-jev-gate-state.json` / `.tmp-jev-gate-questions.json` | 本轮 JEV 门禁（HTTP 400） |

均为 `.tmp-` 前缀且不在 `build.files` 内，**不会进安装包**；步骤 7 只列清单，须获用户确认后才删除。

### E. 预研探针保留，不接入主流程

`.tmp-uia-probe/`（`probe.ps1` / `dump.ps1` / `warm.ps1`）按用户要求**保留，不删除、不接入主流程**。它们只用于量化备用通道覆盖率；步骤 3 的产品代码必须是重新实现的、独立的 `selection-reader.js`，**不得直接调用或依赖这些探针**。

### F. 新步骤 0 期间禁止引入任何依赖

在用户确认技术方案前，**不得**新增 npm 依赖、原生模块或第三方库，**尤其禁止**键盘 Hook 库与大型自动化库。这条同时约束预研脚本与产品代码。桥接方案上限两种（见「关键技术决策一」），如两者都不可行，**停下汇报**而不是引入新库。

### G. 录音链路是回归基线，不得改动

`Ctrl+Shift+L` → ASR → 净化 → 翻译 → 悬浮窗 → 朗读，这一整条链路在本阶段**只读不写**。步骤 6 的任何改动都必须是**追加式**（`globalShortcut.register` 追加语义），且必须通过录音回归。

## 不在本计划内

按 §4.2 阶段 5 合同，仍需用户单独点名：

- 自动粘贴到其它软件（系统 Hook / Win32 SendInput）
- **模拟按键（SendInput）或键盘 Hook（`SetWindowsHookEx`）** —— 明确排除，用户已决定「不拦截 Ctrl+C、不模拟 Ctrl+C」
- **剪贴板历史、剪贴板管理器、剪贴板同步**
- **默认监听并翻译用户每一次普通复制** —— 明确排除，必须是显式双复制
- 开机自启（Run 注册表项 / Startup 文件夹）
- 按住说话 / 松开结束
- 历史记录（本地 sqlite + UI 时间线）
- 术语表（中英对照 + 翻译前注入）
- 运行中切换桥接方案（A / B）或切换划词触发手势
- 完整 Windows 输入法集成（TSF/IME 完整版）—— 本计划的划词**不是**这个，只是「双 Ctrl+C 后读剪贴板」+ UIA 备用
